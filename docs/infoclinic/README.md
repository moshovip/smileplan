# Автоматизация клиники через API «Инфоклиника» (Инфодент)

Поэтапный план внедрения: перевод бумажного регламента «Система проведения приёма пациента
"Первичного у доктора"» и еженедельного отчёта в автоматический контур
**Инфоклиника ↔ SmilePlan ↔ Telegram/BI**.

Документ — рабочий: по нему ставятся задачи, считаются сроки и принимается результат каждого этапа.

---

## 1. Что автоматизируем

### 1.1 Регламент приёма (11 шагов) — исходник

| # | Шаг | Примечание из регламента | Где живёт данные сейчас |
|---|-----|--------------------------|--------------------------|
| 1 | Подготовка к приёму | примечания к назначению, дневники врачей, координатора, КТ, фотопротокол | Инфоклиника (карта, назначения), КТ-хранилище |
| 2 | Приём без опозданий | «галочки» / готовность кабинета / ожидаем пациента в кабинете | нигде (устно) |
| 3 | Встреча пациента | внешний вид / приветствие / знакомство | нигде |
| 4 | Сбор анамнеза / повода обращения | анкета | бумага / карта |
| 5 | Осмотр, фотопротокол, КТ | описание в карте | Инфоклиника |
| 6 | Постановка диагноза | описание в карте | Инфоклиника |
| 7 | Рекомендации | всё озвученное, направления к смежным, договорённости, причины отказа/переноса | Инфоклиника, поле «Рекомендации» |
| 8 | Планы лечения | по поводу обращения / основной / альтернативный | Инфоклиника + SmilePlan |
| 9 | Запись в расписание | проводить пациента, проговорить администратору договорённости, запись с комментарием | Инфоклиника, расписание |
| 10 | Постановка в очередь | подробный комментарий (повод, договорённости) | Инфоклиника, лист ожидания |
| 11 | Заполнение карты | день в день | Инфоклиника |

**Контроль 4-х пунктов на каждом приёме:** 1) с чем пришёл, 2) что лечили, 3) что рекомендовано, 4) с чем ушёл.

### 1.2 Еженедельный отчёт по пациентам — исходник

1. Количество первичных у доктора
2. Количество комплексных консультаций (терапевт / имплантолог / ортопед / ортодонт / гнатолог)
3. Кол-во планов / сумма
4. Кол-во реализованных планов / сумма
5. Кол-во нереализованных планов / причина
6. Кол-во установленных имплантов / брекетов / сумма
7. Кол-во планируемых имплантов / брекетов до конца месяца

### 1.3 Цель автоматизации

| Боль сегодня | После внедрения |
|---|---|
| Чек-лист живёт на бумаге, соблюдение не измеряется | Цифровой чек-лист привязан к визиту, % соблюдения виден по врачу |
| Врач тратит 10–20 мин после приёма на карту, часть карт «не день в день» | Голос → структурированный черновик карты за 60–90 сек, автопроверка «день в день» |
| Отчёт собирается руками (4–6 часов/нед у старшего администратора) | Отчёт формируется автоматически, в понедельник 09:00 в Telegram |
| Причины отказа от плана — свободный текст, не агрегируются | Справочник причин, обязательное поле, срез по причинам |
| Договорённости теряются между врачом и ресепшн | Договорённость = структурированная задача администратору с дедлайном |

**Целевые KPI через 6 месяцев:** соблюдение чек-листа ≥ 90 %, карты «день в день» ≥ 95 %,
время на заполнение карты −60 %, конверсия план → реализация +10 п.п.,
сборка отчёта — 0 человеко-часов.

## 2. Исходные условия по API «Инфоклиники»

Подтверждено на текущий момент:

- МИС «Инфоклиника»/«Инфодент» (Smart Delta Systems / ПРОГ-ТЕХ) поддерживает **REST API** и **HL7**.
- Доступ выдаётся по договору: **домен МИС** + **ключ домена**; заявка на интеграцию —
  в коммерческий отдел (bill@prog-tech.ru), общие вопросы — info@sdsys.ru.
- Часть функций (внешние порталы, получение протоколов через API, расширенная интеграция)
  включается **тарифными опциями** — их нужно явно заказать.
- Онлайн-запись через API поддерживает просмотр свободных слотов в реальном времени
  и блокировку слота на стороне МИС (защита от двойной записи).
- Под МИС — **Firebird**; для тяжёлой аналитики правильный путь — выгрузка/реплика в отдельную БД,
  а не запросы к боевой базе.

**Публичного описания методов нет** — полный перечень приходит с документацией по договору.
Поэтому план построен так, чтобы этап 0 закрыл этот пробел, а архитектура не зависела от
конкретных имён методов: весь обмен изолирован в слое `infoclinic-adapter` (см. §4.2).

**Риск, который снимаем первым:** если какой-то операции (например, записи «Рекомендаций» в карту)
в API нет — переходим на fallback для этой сущности (HL7-сообщение, обмен файлами, реплика БД на чтение,
ручной перенос из SmilePlan). Решение принимается на этапе 0 и фиксируется в матрице покрытия.

### 3.1 Правила владения данными (источник истины)

| Сущность | Источник истины | Направление |
|---|---|---|
| Пациент, контакты | Инфоклиника | МИС → SmilePlan (read) |
| Расписание, слоты, визиты | Инфоклиника | двусторонне (запись через API с блокировкой слота) |
| Прайс-лист, коды услуг | Инфоклиника | МИС → SmilePlan (read, ночной sync) |
| Мед. карта, диагноз, протокол | Инфоклиника | SmilePlan → МИС (черновик), финальный текст в МИС |
| План лечения (черновик, альтернативы, презентация пациенту) | SmilePlan | SmilePlan → МИС (утверждённый план) |
| Чек-лист приёма, договорённости, причины отказа | SmilePlan | SmilePlan → МИС (в «Рекомендации»/комментарий) |
| Финансы, оплаты, реализация | Инфоклиника | МИС → аналитика (read) |

Принцип: **МИС не теряет роль первичной системы**. SmilePlan — «слой рутины»: чек-лист,
голосовой ввод, план лечения, задачи, отчётность. Ничего критичного не существует только в SmilePlan.

## 4. Этапы внедрения

Общая длительность — **20 недель** (≈5 месяцев) при команде 1 backend + 1 frontend (0.5 ставки) +
1 аналитик/владелец процесса со стороны клиники. Этапы 2–6 дают ценность по отдельности —
можно останавливаться на любом.

---

### Этап 0. Доступ, аудит, матрица покрытия — недели 1–2

**Цель:** к концу этапа мы точно знаем, что API умеет, и имеем работающий тестовый контур.

Задачи:

1. Заявка в коммерческий отдел МИС на доступ к API: получить **документацию, домен, ключ домена**,
   список включённых тарифных опций (внешние порталы, получение протоколов, расширенная интеграция).
2. Запросить **тестовый (демо) контур** — писать в боевую базу до этапа 4 запрещено.
3. Выгрузить справочники: врачи, специальности, кабинеты, типы приёма
   («первичный», «комплексная консультация»), прайс-лист с кодами, статусы визитов, лист ожидания.
4. Заполнить **матрицу покрытия API** (ключевой артефакт этапа):

   | Операция | Метод API | Есть? | Fallback |
   |---|---|---|---|
   | Список врачей/специальностей | | | |
   | Свободные слоты на период | | | |
   | Создание/перенос/отмена записи | | | |
   | Карточка пациента по id/телефону | | | |
   | Список визитов за период + статус | | | |
   | Чтение мед. карты / протокола приёма | | | |
   | **Запись** текста в карту / «Рекомендации» | | | |
   | Планы лечения: чтение / создание | | | |
   | Выполненные услуги + суммы | | | |
   | Оплаты, задолженность | | | |
   | Лист ожидания (очередь) + комментарий | | | |
   | Вебхуки / события (или только polling) | | | |

5. Юридический блок: ДС к договору об обработке ПДн (152-ФЗ), регламент доступа,
   решение по ASR/LLM — **обезличивание перед отправкой во внешние модели** либо on-prem ASR.
6. Аудит процесса «как есть»: замер времени на 10 приёмах (шаги 1, 5–8, 11), 5 интервью
   (врач, координатор, администратор, старший администратор, владелец).

**Выход этапа:** матрица покрытия, тестовый доступ, ADR по fallback-ам, baseline-метрики
(время на карту, % карт день в день, часы на отчёт) — без baseline эффект внедрения не доказать.

### Этап 1. Коннектор и синхронизация «на чтение» — недели 3–5

**Цель:** данные МИС доступны сервисам SmilePlan, боевая база не затронута.

Задачи:

1. Сервис `infoclinic-adapter` (Node/TS): единая точка обращения к МИС.
   - хранение `domain` + `domain_key` в секрет-хранилище (не в репозитории, не в PWA);
   - retry с экспоненциальной паузой, circuit breaker, лимит RPS, таймауты;
   - логирование всех вызовов (кто, что, когда — для аудита ПДн);
   - типизированные DTO + версионирование контракта.
2. Сервис `sync-service` + Postgres:
   - таблица соответствий `external_map(entity, local_id, infoclinic_id, updated_at, hash)`;
   - инкрементальная синхронизация (по `updated_at`/дате визита), идемпотентность по `infoclinic_id`;
   - при отсутствии вебхуков — polling: расписание каждые 2–5 мин, справочники раз в сутки.
3. Синхронизируем на чтение: пациенты (по мере обращения, не всю базу), расписание на 14 дней вперёд,
   визиты за 90 дней назад, прайс-лист, врачи, специальности.
4. SmilePlan (сейчас — офлайн-PWA на IndexedDB: `patients`, `plans`, `priceItems`, `appointments`,
   `medRecords`, `roadmaps`, `settings`) получает:
   - endpoint `/sync/pull` (дельта по сущностям) и `/sync/push` (outbox, см. этап 4);
   - поле `externalId` в локальных записях, чтобы дубликаты не плодились;
   - индикатор «синхронизировано / локальный черновик» в интерфейсе.

**Критерий приёмки:** расписание врача на завтра в SmilePlan совпадает с МИС; прайс-лист совпадает
до кода услуги; расхождение по 100 случайным записям = 0; нагрузка на МИС в пике < согласованного лимита.

### Этап 2. Цифровой чек-лист приёма (шаги 1–3, 11) — недели 6–8

**Цель:** регламент с бумаги переезжает в экран и начинает измеряться.

Задачи:

1. **Карточка подготовки к приёму (шаг 1)** — экран, который собирается автоматически за 15 мин
   до визита: повод обращения, примечания к назначению, последние дневники врачей и координатора,
   наличие КТ и фотопротокола, долг, незакрытые планы, договорённости с прошлого визита.
   Врач открывает один экран вместо пяти вкладок МИС.
2. **Чек-лист визита** — привязан к `appointment.externalId`, 11 пунктов, отметка в один тап,
   фиксируется время отметки:

```json
{
  "appointmentId": "IC-482913",
  "doctorId": "IC-D-17",
  "checklist": {
    "prep":        {"done": true,  "at": "2026-09-18T09:42:11Z"},
    "onTime":      {"done": true,  "at": "2026-09-18T10:00:04Z", "delayMin": 0},
    "greeting":    {"done": true,  "at": "2026-09-18T10:01:30Z"},
    "anamnesis":   {"done": true,  "at": "2026-09-18T10:09:00Z", "formId": "anketa-v2"},
    "examPhotoCT": {"done": true,  "photos": 8, "ct": true},
    "diagnosis":   {"done": true},
    "recommend":   {"done": false},
    "plans":       {"done": false},
    "booking":     {"done": false},
    "queue":       {"done": false, "notApplicable": true},
    "chartFilled": {"done": false, "dueAt": "2026-09-18T23:59:59Z"}
  }
}
```

3. **Готовность кабинета (шаг 2):** отметка ассистента «кабинет готов» → статус визита в SmilePlan;
   если за 10 мин до приёма отметки нет — пуш старшему администратору.
   Опоздание считается автоматически: `фактический старт − плановый` из расписания МИС.
4. **Анкета (шаг 4)** — веб-форма, ссылка уходит пациенту в SMS/Telegram за сутки; заполненная
   анкета подтягивается в карточку подготовки. Если не заполнена — планшет на ресепшн.
5. Отчёт «соблюдение регламента»: % выполненных пунктов по врачу/неделе, среднее опоздание.

**Критерий приёмки:** 2 недели пилота на 2 врачах, ≥ 80 % визитов с заполненным чек-листом,
время заполнения чек-листа ≤ 60 сек за приём.

### Этап 3. Карта, рекомендации, планы: голос + AI (шаги 5–8, контроль 4 пунктов) — недели 9–12

**Цель:** убрать главную рутину — ручной набор текста, — не потеряв качество записи.

Задачи:

1. **Голосовой ввод осмотра и диагноза.** Врач диктует → ASR → LLM раскладывает в структуру:
   зубная формула, состояние по зубам, диагноз (с кодом МКБ-10/классификатором клиники),
   рекомендации. В SmilePlan уже есть голосовой ввод и подбор по прайсу — расширяем до полного
   протокола и до записи результата в МИС.
   **ПДн:** перед отправкой во внешнюю модель — обезличивание (замена ФИО/телефона/даты рождения на
   плейсхолдеры, обратная подстановка локально) либо on-prem ASR + локальная модель. Решение — из этапа 0.
2. **Фотопротокол и КТ (шаг 5):** загрузка фото с телефона в визит, автопривязка к пациенту,
   контроль «фото есть/нет» в чек-листе.
3. **Рекомендации (шаг 7) — структурированно**, а не свободным текстом:
   - что озвучено пациенту (список);
   - направления к смежным специалистам (специальность + срок);
   - договорённости (текст + дата + ответственный);
   - **причина отказа/переноса лечения — из справочника** (цена, время, «подумаю», страх,
     нужна консультация смежника, лечится в другом месте, сомнения в необходимости, иное + текст).
   Справочник причин — отдельный артефакт этапа, без него не собирается п.5 еженедельного отчёта.
4. **Планы лечения (шаг 8):** три слота — «по поводу обращения», «основной», «альтернативный»;
   позиции из синхронизированного прайса, суммы, срок актуальности, статус
   (`черновик → презентован → согласован → в работе → реализован → отклонён`).
   PDF/HTML-смета пациенту — уже есть в SmilePlan, привязываем к `externalId` визита.
5. **Контроль 4 пунктов** — генерируется автоматически из уже введённых данных и показывается врачу
   на подтверждение в конце приёма:

   | Пункт | Источник |
   |---|---|
   | С чем пришёл | повод обращения + анкета (шаг 4) |
   | Что лечили | выполненные услуги визита (МИС) |
   | Что рекомендовано | блок «Рекомендации» (шаг 7) |
   | С чем ушёл | статус плана + запись/очередь (шаги 9–10) |

   Если один из четырёх пуст — визит нельзя закрыть без явного «неприменимо» с комментарием.
6. **Запись обратно в МИС:** структурированный текст протокола и рекомендаций отправляется в карту
   через API (метод из матрицы этапа 0). Нет метода записи → fallback: формируем готовый текст и
   отдаём его врачу в буфер обмена/файлом, а «день в день» контролируем по факту появления
   протокола в МИС (чтение).

**Критерий приёмки:** среднее время оформления карты после приёма ≤ 5 мин (baseline из этапа 0),
доля протоколов, принятых врачом без правок > 60 %, 100 % отказов имеют код причины.

### Этап 4. Запись, очередь, задачи администратору (шаги 9–10) — недели 13–14

Здесь начинается **запись в боевую МИС** — только после успешных этапов 1–3 на тесте.

Задачи:

1. **Запись в расписание из SmilePlan:** свободные слоты из МИС → выбор → блокировка слота на
   стороне МИС → создание визита с **комментарием по шаблону** (повод, договорённости, что подготовить).
   Шаблон комментария обязателен — это то, что в регламенте «проговариваем администратору».
2. **Передача на ресепшн:** карточка «пациент идёт к вам» — договорённости, план, сумма, что записать,
   что взять с собой. Администратор видит её до того, как пациент дошёл до стойки.
3. **Лист ожидания / очередь (шаг 10):** постановка с обязательным структурированным комментарием
   (повод + договорённости + желаемый период) и автонапоминанием ответственному.
4. **Задачи и напоминания:** договорённость из шага 7 → задача с дедлайном → Telegram/пуш
   ответственному; эскалация старшему администратору при просрочке.
5. **Идемпотентность и защита от дублей:** outbox-паттерн, ключ идемпотентности на каждую операцию
   записи, повтор при сетевой ошибке не создаёт второй визит; все операции записи — в аудит-лог.
6. **Rollback-план:** фича-флаг на запись в МИС, «тихий режим» (операция логируется, но не отправляется)
   для первой недели.

**Критерий приёмки:** 0 дублей визитов за 2 недели, 100 % визитов из SmilePlan имеют комментарий,
среднее время записи пациента −50 %.

### Этап 5. Еженедельный отчёт и дашборд — недели 15–17

**Цель:** отчёт из семи пунктов собирается сам.

Задачи:

1. **Витрина данных:** ночной ETL из МИС (реплика/выгрузка) + данные SmilePlan → `analytics` (Postgres).
   Тяжёлые агрегации — только по витрине, не по боевой базе.
2. **Формализовать метрики** (каждая — SQL + определение, согласованное с владельцем процесса):

   | # | Метрика | Формула / определение |
   |---|---|---|
   | 1 | Первичные у доктора | визиты с типом «первичный», статус «выполнен», группировка по врачу и неделе |
   | 2 | Комплексные консультации | визиты типа «компл. консультация» × специальность (терап/импл/ортопед/ортодонт/гнатолог) |
   | 3 | Планы / сумма | планы, созданные за период, статус ≥ «презентован»; сумма по позициям прайса |
   | 4 | Реализованные планы / сумма | план, где выполнено и оплачено ≥ порога (по умолчанию 80 % суммы); сумма — по фактически выполненным услугам |
   | 5 | Нереализованные / причина | планы со статусом «отклонён»/просроченные, разрез по коду причины из справочника (этап 3) |
   | 6 | Установленные импланты / брекеты / сумма | выполненные услуги с кодами групп «имплантация» / «ортодонтия-фиксация», счёт единиц и суммы |
   | 7 | Планируемые импланты / брекеты до конца месяца | будущие визиты + очередь с этими кодами до последнего дня текущего месяца |

   Отдельно фиксируем спорные определения: что считать «реализованным» планом, как учитывать
   частичную реализацию, как считать перенос на следующий месяц. Это решение клиники, а не разработчика.
3. **Автоотчёт:** понедельник 09:00 — Telegram (в SmilePlan уже есть отправка в Telegram): сводка по клинике,
   разрез по врачам, динамика к прошлой неделе, топ-3 причины отказа. Полная версия — ссылкой на дашборд.
4. **Дашборд** в SmilePlan: неделя/месяц, фильтр по врачу и специальности, drill-down до конкретного плана.
5. **Сверка:** первые 4 недели отчёт считается и автоматически, и вручную; расхождение > 2 % — разбор.

**Критерий приёмки:** 4 недели подряд расхождение с ручным отчётом ≤ 2 %, время подготовки отчёта — 0 ч.

### Этап 6. Контроль качества, эскалации, приживаемость — недели 18–20

Задачи:

1. **«День в день» (шаг 11):** в 20:00 бот присылает врачу список незакрытых карт за сегодня;
   в 09:00 следующего дня — старшему администратору список просроченных.
2. **Контроль воронки:** план презентован, но нет записи 7 дней → задача координатору;
   план согласован, но нет оплаты/визита 14 дней → задача.
3. **Рейтинг соблюдения регламента** по врачам (без публичного шейминга — для разбора на планёрке).
4. **Обучение и приживаемость:** инструкции на 1 страницу по роли, 2 тренировки, «сопровождающий»
   первые 2 недели, сбор обратной связи, еженедельный разбор 3 доработок.
5. **Стабилизация:** мониторинг (доступность API МИС, очередь outbox, ошибки синхронизации),
   алерты в Telegram, дежурный регламент.

**Критерий приёмки:** карты «день в день» ≥ 95 %, соблюдение чек-листа ≥ 90 %, ноль критичных инцидентов
синхронизации за 2 недели.

## 6. Технические решения, которые нельзя пропустить

- **Антикоррупционный слой.** Ни один модуль, кроме `infoclinic-adapter`, не знает о форматах МИС.
  Смена версии API = правка одного пакета.
- **Идемпотентность записи.** Ключ на каждую операцию + outbox. Повтор из-за сети не создаёт дубль визита.
- **Офлайн.** SmilePlan — PWA на IndexedDB, врач работает без сети; очередь изменений уходит при появлении связи.
  Конфликт разрешается по правилам §3.1 (расписание и финансы — всегда МИС).
- **Секреты.** `domain_key` — только на сервере, в секрет-хранилище; в браузер не попадает никогда.
  Доступ к API — с фиксированных IP/через VPN, если МИС это поддерживает.
- **ПДн (152-ФЗ).** Минимизация: тянем только нужные поля; обезличивание перед LLM; журнал доступа;
  срок хранения; ДС с подрядчиками. Согласие пациента на обработку — в анкете этапа 2.
- **Нагрузка на МИС.** Лимит RPS, ночные окна для тяжёлых выгрузок, кэш справочников,
  аналитика — только по витрине.
- **Наблюдаемость.** Метрики: лаг синхронизации, длина outbox, доля ошибок API, время ответа МИС.
  Алерт в Telegram при лаге > 10 мин.

## 7. Риски и их снятие

| Риск | Вероятность | Влияние | Что делаем |
|---|---|---|---|
| В API нет записи в карту/планы | средняя | высокое | матрица покрытия на этапе 0; fallback — буфер обмена/файл + контроль по чтению |
| Нужная функция закрыта тарифной опцией | средняя | среднее | список опций и стоимость запрашиваем на этапе 0, до начала разработки |
| Нет вебхуков, только polling | высокая | среднее | инкрементальный polling + кэш; согласовать лимит RPS |
| Сопротивление врачей («ещё одна программа») | высокая | высокое | чек-лист ≤ 60 сек, голос вместо клавиатуры, пилот на 2 лояльных врачах, участие в доработках |
| Двойной ввод (МИС + SmilePlan) | средняя | высокое | этап 4 (запись обратно) — обязательный, не «опциональный» |
| Расхождение цифр с ручным отчётом | средняя | среднее | 4 недели параллельного счёта, письменные определения метрик |
| Утечка ПДн через LLM | низкая | критическое | обезличивание/on-prem, запрет отправки ФИО и контактов, журнал |
| Обновление МИС ломает интеграцию | средняя | среднее | версионирование адаптера, контрактные тесты на тестовом контуре, дымовой тест после обновлений |

## 8. Ресурсы и порядок запуска

**Команда:** backend (1.0), frontend/PWA (0.5), владелец процесса со стороны клиники (0.3),
старший администратор как «носитель регламента» (0.2), ИТ-подрядчик МИС — по запросу.

**Порядок, если нужно быстрее увидеть эффект:** этап 0 → этап 5 (отчёт: максимум ценности при
минимуме записи в МИС — только чтение) → этап 2 (чек-лист) → этап 3 → этап 4 → этап 6.
Такой порядок даёт владельцу цифры уже на 6–7-й неделе.

**Точки принятия решения:**
- после этапа 0 — подтверждаем объём (матрица покрытия может сократить или расширить план);
- после этапа 2 — решаем, катим ли на всю клинику или дорабатываем по обратной связи;
- перед этапом 4 — отдельное «да» на запись в боевую МИС.
