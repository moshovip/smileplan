# Голосовая автоматизация приёма в МИС «Инфоклиника» с соблюдением 152-ФЗ

Задача: врач и администратор перестают **набирать руками** то, что сейчас вбивается в «Инфоклинику»
после каждого приёма. Всё, что можно, вводится **голосом**, попадает в МИС **через API**,
а обработка данных о здоровье пациентов остаётся законной по 152-ФЗ.

Документ — рабочий план внедрения: по нему запрашивается доступ к API, ставятся задачи подрядчику
и принимается результат каждого этапа.

> Правовой раздел (§2) — не юридическое заключение. Итоговые формулировки согласий и приказов
> подписывает юрист клиники, сверяясь с действующей редакцией 152-ФЗ на дату внедрения
> (закон правился в 2024–2025 гг., часть изменений вступает в силу в 2026 г.).

---

## 1. Что автоматизируем

Основа — действующий регламент клиники «Система проведения приёма пациента "Первичного у доктора"»
(11 шагов), контроль 4 пунктов на каждом приёме и еженедельный отчёт из 7 показателей
(исходник — `reglament-priem-source.jpg` рядом с этим файлом).

### 1.1 Разделение: что голосом, что одной кнопкой, что остаётся как есть

Голос эффективен там, где сейчас набирается текст. Там, где нужен выбор из списка или подтверждение —
быстрее и надёжнее один тап. Навязывать голос везде — главная ошибка таких внедрений.

| Шаг регламента | Способ ввода | Что происходит в «Инфоклинике» |
|---|---|---|
| 1. Подготовка к приёму | чтение с экрана | ничего не пишем, только читаем через API (досье к визиту) |
| 2. Приём без опозданий | кнопка/голос «кабинет готов» | отметка статуса визита |
| 3. Встреча пациента | кнопка | отметка чек-листа |
| 4. Анамнез / повод обращения | **голос** + анкета онлайн | текст в карту, поле «повод обращения» |
| 5. Осмотр, фотопротокол, КТ | **голос** (руки заняты — педаль/гарнитура) | описание осмотра в карту, зубная формула |
| 6. Постановка диагноза | **голос** + подтверждение кода | диагноз + код в карту |
| 7. Рекомендации | **голос**, раскладка по структуре | поле «Рекомендации»: озвучено / направления / договорённости / причина отказа |
| 8. Планы лечения | **голос** («имплантация 36, коронка 36…») | позиции плана по кодам прайса, 3 плана: по поводу / основной / альтернативный |
| 9. Запись в расписание | **голос** + выбор слота тапом | создание визита с комментарием по шаблону |
| 10. Постановка в очередь | **голос** | лист ожидания + структурированный комментарий |
| 11. Заполнение карты | автоматически из шагов 4–8 | протокол приёма в карте, «день в день» контролируется системой |
| Контроль 4 пунктов | собирается сам, врач подтверждает | с чем пришёл / что лечили / что рекомендовано / с чем ушёл |
| Еженедельный отчёт (7 п.) | голосовой запрос или по расписанию | только чтение из МИС + витрина, никакой ручной сборки |

### 1.2 Целевой эффект

| Сейчас | После |
|---|---|
| 10–20 мин набора карты после приёма, часть карт не «день в день» | диктовка 60–90 сек + подтверждение, карта закрыта до ухода пациента |
| Договорённости передаются устно и теряются | договорённость произнесена → задача администратору с дедлайном |
| Причины отказа — свободный текст, не считаются | код причины из справочника, обязательное поле |
| Отчёт собирается руками 4–6 ч/нед | формируется автоматически |

Ориентир по скорости: вендоры голосового ввода для медицины заявляют ввод в 4–8 раз быстрее клавиатуры
и сокращение времени описания на ~30 %. Проверяем на своём замере (§5, этап 0), а не на слово.

## 2. Правовая рамка 152-ФЗ — она определяет архитектуру

Это не «раздел для галочки»: именно закон решает, где будет стоять распознавание речи.

### 2.1 Что за данные мы трогаем

- Сведения о состоянии здоровья — **специальная категория ПДн** (ст. 10 152-ФЗ). Обработка по общему
  правилу запрещена, но разрешена, когда она нужна в медико-профилактических целях, для постановки
  диагноза и оказания медицинских услуг — **при условии, что обработку ведёт лицо, профессионально
  занимающееся медицинской деятельностью и обязанное сохранять врачебную тайну** (ст. 10 ч. 2;
  врачебная тайна — ст. 13 323-ФЗ).
- Ключевой вывод: **ИТ-подрядчик и облачный сервис распознавания речи таким лицом не являются.**
  Как только аудио или текст приёма уходит во внешний сервис — это передача данных о здоровье третьему
  лицу, и «медицинское» исключение больше не работает само по себе. Нужны поручение на обработку по
  ст. 6 ч. 3 (договор с перечнем действий, целями, обязанностью конфиденциальности и мерами защиты)
  и согласие пациента.

### 2.2 Отсюда — главное архитектурное решение

**Распознавание речи и разбор текста разворачиваются в контуре клиники (on-premise), аудио не покидает
периметр.** Тогда данные остаются у оператора-клиники, «медицинское» исключение ст. 10 применимо,
трансграничной передачи нет, требование локализации баз данных в РФ (ст. 18 ч. 5) выполняется автоматически.

Это **дешевле по юридическим издержкам**, чем любая облачная схема: не нужны отдельные согласия на передачу
данных о здоровье вовне, не нужен аудит подрядчика, не нужна оценка вреда субъектам при утечке у третьего лица.

Прямо запрещаем себе (см. §6): отправку аудио или текста приёма в зарубежные сервисы (ChatGPT, Gemini и
любые API за пределами РФ) — это нарушение локализации и трансграничной передачи спецкатегории ПДн,
с 2025 г. — зона оборотных штрафов, а при умышленной передаче — ст. 272.1 УК РФ.

### 2.3 Голос — это биометрия?

Нет, если соблюсти условие. Биометрические ПДн (ст. 11) — это данные о физиологических особенностях,
на основании которых можно установить личность, **и которые оператор использует для установления личности**.
Мы используем голос только как способ ввода текста, не для идентификации по голосу.
Это нужно **прямо зафиксировать** в политике обработки ПДн и в техдокументации:
«голосовые данные не используются для идентификации субъекта, голосовые модели не строятся,
биометрический шаблон не формируется». Иначе рискуем попасть под режим ст. 11 и ЕБС.

### 2.4 Чей голос записываем — принципиальный выбор

| Вариант | Что записывается | Правовая нагрузка | Рекомендация |
|---|---|---|---|
| **A. Диктовка врача (push-to-talk)** | только речь врача, по нажатию | минимальная: врач — работник, обязан хранить врачебную тайну; пациент не записывается | **старт отсюда** |
| B. Запись всего приёма (ambient) | диалог врача и пациента | нужно отдельное информированное согласие пациента на аудиозапись, хранение, доступ; выше риск | только вторым шагом, после отладки A |

Вариант A закрывает 80 % рутины и почти не создаёт новых правовых обязательств. Начинаем с него.

### 2.5 Минимизация и срок хранения аудио

- Аудио обрабатывается **потоком** и удаляется сразу после распознавания (целевое состояние).
- Если для отладки качества нужны записи — только с обезличиванием, в отдельном хранилище,
  ограниченный круг доступа, срок не более 30 суток, и это описано в локальных актах.
- «Оставим на всякий случай навсегда» — прямое нарушение принципа минимизации (ст. 5) и лишний риск.

### 2.6 Обязательный организационный пакет

- [ ] Ответственный за организацию обработки ПДн (приказ, ст. 22.1)
- [ ] Уведомление в Роскомнадзор об обработке ПДн — актуализировать: добавить голосовой ввод как способ
      обработки и новые ИСПДн (ст. 22)
- [ ] Политика обработки ПДн — дополнить голосовым вводом и пунктом 2.3 (голос ≠ идентификация)
- [ ] Перечень ИСПДн, модель угроз, определение **уровня защищённости** по ПП РФ № 1119
      (спецкатегория → как правило УЗ-2; итог зависит от актуальных угроз и числа субъектов)
- [ ] Меры защиты по приказу ФСТЭК России № 21 под выбранный УЗ; при использовании криптографии —
      приказ ФСБ России № 378
- [ ] Согласия и договоры: обновлённое согласие пациента (перечень действий: аудиозапись речи врача,
      автоматизированная обработка), поручения на обработку с подрядчиком и с вендором МИС (ст. 6 ч. 3),
      NDA и обязательства о врачебной тайне для всех, кто получает доступ
- [ ] Журнал доступа к ПДн, регламент реагирования на инциденты: уведомление РКН **в течение 24 часов**
      о факте инцидента и **72 часов** — о результатах внутреннего расследования (ст. 21)
- [ ] Инструктаж и подписи сотрудников

**Ответственность, о которой стоит знать владельцу:** с 30.05.2025 (ФЗ № 420-ФЗ) за утечку ПДн введены
оборотные штрафы, ужесточена ст. 13.11 КоАП, действует ст. 272.1 УК РФ за незаконные использование
и передачу персональных данных. Это аргумент в пользу on-prem, а не «сэкономим на сервере».

## 3. Архитектура

```
  Кабинет врача                        Серверная клиники (контур ПДн)
┌────────────────────┐            ┌──────────────────────────────────────┐
│ гарнитура + педаль │  аудио     │  ASR on-prem (речь → текст)          │
│ push-to-talk       │───────────►│  словарь стоматологии, коды зубов    │
│ планшет/моноблок   │            └───────────────┬──────────────────────┘
│ экран подтверждения│◄──черновик─────────────────┤
└─────────┬──────────┘                            ▼
          │ «подтверждаю»          ┌──────────────────────────────────────┐
          └───────────────────────►│  NLU/разбор on-prem:                 │
                                   │  текст → структура (JSON) по шагам   │
                                   │  4–8 регламента, коды прайса, МКБ    │
                                   └───────────────┬──────────────────────┘
                                                   ▼
                                   ┌──────────────────────────────────────┐
                                   │  integration-service                 │
                                   │  очередь, идемпотентность, аудит-лог │
                                   └───────┬──────────────────┬───────────┘
                                REST API   │                  │ чтение
                                домен+ключ ▼                  ▼
                                   ┌───────────────┐   ┌──────────────────┐
                                   │ «Инфоклиника» │   │ витрина отчётов  │
                                   │ карта, план,  │──►│ (ночная выгрузка)│
                                   │ расписание    │   └────────┬─────────┘
                                   └───────────────┘            ▼
                                                        Telegram-бот / дашборд
```

**Ничего из этого не выходит в интернет, кроме самого API «Инфоклиники»** (и то — внутри контура,
если МИС стоит локально).

### 3.1 Три варианта реализации голосового слоя

| | A. Готовый вендор (напр. Voice2Med / ЦРТ) | B. Своя разработка on-prem | C. Гибрид (рекомендуется) |
|---|---|---|---|
| Что это | коробочное решение голосового заполнения медицинской документации, работает on-prem, есть **словарь стоматолога**, интеграция с МИС по FormAPI, ввод в активное поле любой программы | своё: открытая ASR-модель на сервере клиники + локальная языковая модель для разбора | вендорский ASR как «голос → текст» + свой сервис, который превращает текст в структуру и пишет в API «Инфоклиники» |
| Срок | быстро (недели) | долго (месяцы) | средне |
| Правовая часть | закрыта вендором, нужно проверить документы | делаем сами | проще всего |
| Гибкость под наш регламент | низкая (диктовка в поле, не логика) | максимальная | достаточная |
| Деньги | лицензии на рабочее место | сервер + разработка | лицензии + меньше разработки |

**Рекомендация:** пилот по варианту C. Диктовку отдаём готовому медицинскому ASR (он уже умеет
стоматологические термины и номера зубов — самое трудное), а всю логику регламента, планы лечения,
договорённости, задачи и отчёты делаем своим сервисом поверх API «Инфоклиники».

При запросе КП у вендора обязательно спросить: работа **полностью офлайн** (без обращения в облако),
наличие словаря стоматологии, формат интеграции (эмуляция клавиатуры vs API), требования к серверу
(GPU/CPU), стоимость на рабочее место, документы по защите информации.

### 3.2 Принцип «решение принимает человек»

Система **никогда не пишет в карту молча**. Порядок всегда: врач продиктовал → на экране черновик →
врач подтверждает (кнопка или голосовая команда «подтверждаю») → запись уходит в МИС.
Это и клинически правильно, и снимает вопрос об автоматизированном принятии решений (ст. 16 152-ФЗ).

### 3.3 Технические требования к интеграции с «Инфоклиникой»

- Доступ по паре **домен МИС + ключ домена**, выдаётся по договору; часть функций включается
  тарифными опциями — заказать заранее (см. этап 0).
- Ключ хранится **только на сервере** в секрет-хранилище, никогда — в браузере/планшете врача.
- Весь обмен изолирован в одном модуле-адаптере: меняется версия API — правится один модуль.
- **Идемпотентность**: у каждой операции записи свой ключ, повтор при обрыве связи не создаёт
  второй визит и не дублирует запись в карте.
- Аудит-лог всех обращений: кто, когда, к каким данным, что записал (нужен и для 152-ФЗ, и для разбора).
- Тяжёлая аналитика — **только по ночной выгрузке/реплике**, не по боевой базе.

## 4. Голосовые сценарии (что именно говорит врач)

Режим: **push-to-talk** — ножная педаль или кнопка на гарнитуре. Руки в перчатках, микрофон не слушает
постоянно (это ещё и правовая гигиена: нет непрерывной записи кабинета).

Формат команд: короткое ключевое слово + содержание. Примеры целевых сценариев:

| Что говорит врач | Что делает система |
|---|---|
| «Осмотр. Зуб 36 — глубокая кариозная полость на жевательной поверхности, зондирование болезненно, перкуссия отрицательная» | заполняет описание осмотра, привязывает к зубу 36 в формуле |
| «Диагноз 36 — кариес дентина» | ставит диагноз + подставляет код, врач подтверждает |
| «План основной: имплантация 36, формирователь десны, коронка на импланте 36» | собирает план из позиций прайса по кодам, считает сумму, показывает смету |
| «План альтернативный: мостовидный протез 35–37» | второй план в слот «альтернативный» |
| «Рекомендации: гигиена через две недели, направление к ортодонту в течение месяца» | раскладывает в «озвучено» и «направления к смежным» |
| «Отказ: дорого, вернётся после отпуска в ноябре» | код причины отказа «стоимость» + договорённость с датой → задача координатору |
| «Записать на гигиену через две недели, утро» | показывает свободные слоты из МИС, врач выбирает тапом, визит создаётся с комментарием |
| «В очередь на имплантацию, ждём решения до конца октября» | лист ожидания + структурированный комментарий |
| «Готово» | собирает 4 контрольных пункта, показывает на подтверждение, закрывает визит |
| «Отчёт за неделю» | присылает сводку 7 показателей в Telegram |

Отдельно — **словарь клиники**: номера зубов, названия услуг ровно так, как они звучат у вас,
фамилии врачей, сокращения. Без настроенного словаря качество распознавания разочарует — это
работа этапа 2, а не «оно само».

## 5. Этапы внедрения

20 недель. Команда: backend-разработчик (1.0), интегратор/DevOps в контуре клиники (0.3),
ответственный за ПДн + юрист (0.2), старший администратор как владелец регламента (0.2),
2 врача в пилоте.

### Этап 0. Доступ, право, замеры — недели 1–2

1. Заявка вендору МИС на API: документация, домен, **ключ домена**, тестовый контур, перечень и
   стоимость тарифных опций (внешние порталы, получение протоколов, расширенная интеграция).
2. **Матрица покрытия API** — главный артефакт этапа. По каждой операции: есть метод / нет / fallback.

   | Операция | Метод | Есть? | Fallback |
   |---|---|---|---|
   | Карточка пациента, визиты за период | | | |
   | Свободные слоты, создание/перенос визита | | | |
   | Чтение протокола приёма / мед. карты | | | |
   | **Запись текста в карту и в «Рекомендации»** | | | |
   | Планы лечения: чтение / создание | | | |
   | Выполненные услуги, суммы, оплаты | | | |
   | Лист ожидания + комментарий | | | |
   | События/вебхуки или только опрос | | | |

   Если записи в карту через API нет — fallback: ввод в активное поле МИС (так работает вендорский
   голосовой ввод) либо согласованная выгрузка. Решение фиксируем здесь, до разработки.
3. Правовой блок из §2.6: назначить ответственного, определить УЗ по ПП 1119, запустить модель угроз,
   обновить уведомление РКН и согласия.
4. Замер baseline: время заполнения карты на 10 приёмах, % карт «день в день» за прошлый месяц,
   часы на сборку еженедельного отчёта. Без этих цифр эффект внедрения нечем доказать.
5. КП от вендоров голосового ввода по вопросам из §3.1.

**Выход:** матрица покрытия, тестовый доступ, выбранный вариант A/B/C, baseline, план работ с бюджетом.

### Этап 1. Контур и чтение из МИС — недели 3–5

- Сервер в контуре клиники под ASR и сервисы (по требованиям вендора/модели).
- `integration-service`: адаптер к API, секреты, ретраи, лимит RPS, аудит-лог.
- Чтение: пациенты, расписание на 14 дней, визиты за 90 дней, прайс с кодами, врачи, специальности.
- Экран **«Подготовка к приёму» (шаг 1)**: одно окно вместо пяти вкладок — повод, примечания к
  назначению, дневники врача и координатора, наличие КТ и фото, долг, незакрытые планы,
  договорённости с прошлого визита.

**Приёмка:** расписание и прайс совпадают с МИС на 100 случайных записях; в боевую базу ничего не пишем.

### Этап 2. Голосовая диктовка карты — недели 6–9

- Разворачивание ASR on-prem, гарнитуры/педали в 2 кабинета.
- **Словарь клиники**: зубные формулы, услуги по прайсу, термины, фамилии. Итеративно, по записям пилота.
- Голосом: осмотр (шаг 5), диагноз (шаг 6), анамнез/повод (шаг 4).
- Экран черновика + подтверждение врачом, правка голосом («исправь зуб 36 на 37») и клавиатурой.
- Запись результата в карту (методом из матрицы этапа 0 либо fallback).
- Контроль «день в день»: в 20:00 врачу — список незакрытых карт.

**Приёмка:** точность распознавания на стоматологической лексике ≥ 95 % после настройки словаря;
время оформления карты ≤ 5 мин (против baseline); ≥ 60 % протоколов принимаются без правок.

### Этап 3. Рекомендации, планы, контроль 4 пунктов — недели 10–13

- **Рекомендации (шаг 7) структурно**: озвучено / направления к смежным (специальность + срок) /
  договорённости (текст + дата + ответственный) / **причина отказа или переноса из справочника**.
- **Справочник причин** (8–12 позиций + «иное»): цена, время, «подумаю», страх, ждёт смежника,
  лечится в другом месте, сомнения в необходимости… Без закрытого списка п. 5 отчёта не считается.
- **Планы лечения (шаг 8)**: голосом из позиций прайса, три слота (по поводу обращения / основной /
  альтернативный), сумма, срок актуальности, статусы: черновик → презентован → согласован → в работе →
  реализован → отклонён. Смета пациенту — печать/файл.
- **Контроль 4 пунктов**: собирается автоматически (с чем пришёл — повод и анкета; что лечили —
  выполненные услуги из МИС; что рекомендовано — блок рекомендаций; с чем ушёл — статус плана и запись).
  Визит не закрывается, пока пункт не заполнен или не помечен «неприменимо» с комментарием.

**Приёмка:** 100 % отказов имеют код причины; у 100 % закрытых визитов заполнены 4 пункта.

### Этап 4. Запись в расписание, очередь, задачи — недели 14–15

Первая запись в **боевую** МИС — только после успешных этапов 1–3 на тесте, под фича-флагом
и с «тихим режимом» (операция логируется, но не отправляется) в первую неделю.

- Запись на приём голосом + выбор слота тапом, блокировка слота на стороне МИС (защита от двойной записи),
  **обязательный комментарий по шаблону** (повод, договорённости, что подготовить) — это то, что в
  регламенте «проговариваем администратору».
- Карточка «пациент идёт к вам» для ресепшн: договорённости, план, сумма, что записать.
- Лист ожидания (шаг 10) со структурированным комментарием и напоминанием ответственному.
- Задачи из договорённостей → Telegram ответственному, эскалация старшему администратору при просрочке.

**Приёмка:** ноль дублей визитов за 2 недели, 100 % визитов с комментарием.

### Этап 5. Еженедельный отчёт — недели 16–18

Ночная выгрузка в витрину + формализация семи показателей. Каждое определение согласовано письменно:

| # | Показатель | Определение |
|---|---|---|
| 1 | Первичные у доктора | визиты типа «первичный», статус «выполнен», по врачу и неделе |
| 2 | Комплексные консультации | по специальностям: терапевт / имплантолог / ортопед / ортодонт / гнатолог |
| 3 | Планы / сумма | планы, созданные за период, статус ≥ «презентован» |
| 4 | Реализованные планы / сумма | выполнено и оплачено ≥ порога (по умолчанию 80 % суммы) |
| 5 | Нереализованные / причина | отклонённые и просроченные планы, разрез по коду причины (этап 3) |
| 6 | Установленные импланты / брекеты / сумма | выполненные услуги по кодам групп «имплантация» / «ортодонтия-фиксация» |
| 7 | Планируемые импланты / брекеты до конца месяца | будущие визиты + очередь с этими кодами до конца месяца |

Спорное решаем заранее и письменно: что считать реализованным планом, как учитывать частичную
реализацию и переносы на следующий месяц. Это решение клиники, не разработчика.

Доставка: понедельник 09:00 — сводка в Telegram (клиника, разрез по врачам, динамика к прошлой неделе,
топ-3 причины отказа), полная версия — дашборд. Голосовой запрос «отчёт за неделю» — по желанию.

**Приёмка:** 4 недели параллельного счёта с ручным отчётом, расхождение ≤ 2 %.

### Этап 6. Контроль, эскалации, приживаемость — недели 19–20

- «День в день»: вечером — врачу, утром — старшему администратору список просрочек.
- Воронка: план презентован, но нет записи 7 дней → задача координатору; согласован, но нет оплаты
  14 дней → задача.
- Дашборд соблюдения регламента по врачам (для планёрки, не для публичного шейминга).
- Обучение: инструкция на одну страницу по роли, две тренировки, сопровождающий первые две недели,
  еженедельный разбор трёх доработок по обратной связи.
- Мониторинг: доступность API МИС, очередь операций, ошибки распознавания, алерты в Telegram.

**Приёмка:** карты «день в день» ≥ 95 %, соблюдение чек-листа ≥ 90 %, ноль критичных инцидентов за 2 недели.

## 6. Чего делать нельзя (антипаттерны)

1. **Отправлять аудио или текст приёма в зарубежные сервисы** (ChatGPT, Gemini, любые API вне РФ) —
   нарушение локализации и правил трансграничной передачи спецкатегории ПДн.
2. **Диктовать на личный телефон врача** в мессенджер/заметки — данные о здоровье уходят из контура
   клиники без всякого основания.
3. **Писать весь приём «на всякий случай»** без согласия пациента и без срока хранения.
4. **Хранить ключ API «Инфоклиники»** в приложении на планшете/в браузере — он должен жить только на сервере.
5. **Автоматически писать в карту без подтверждения врача** — клинически и юридически неверно.
6. **Тянуть отчёты прямыми запросами к боевой базе МИС** — риск для работы клиники; только выгрузка/реплика.
7. **Начинать с записи в боевую МИС** до отладки на тестовом контуре.

## 7. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| В API нет записи в карту/планы | высокое | матрица покрытия на этапе 0; fallback — ввод в активное поле МИС |
| Нужная функция закрыта платной тарифной опцией | среднее | список и стоимость опций запрашиваем до начала разработки |
| Качество распознавания на стоматологической лексике ниже ожиданий | высокое | вендор со словарём стоматолога, своя настройка словаря на этапе 2, пилот до закупки на всю клинику |
| Шум кабинета, бормашина, маска | среднее | гарнитура с шумоподавлением, push-to-talk, тест в реальном кабинете, а не в переговорке |
| Сопротивление врачей («ещё одна программа») | высокое | голос вместо клавиатуры, чек-лист ≤ 60 сек, пилот на двух лояльных врачах, их правки в приоритете |
| Двойной ввод (МИС + новая система) | высокое | этап 4 обязателен, не опционален |
| Претензии по ПДн / проверка РКН | критическое | on-prem, пакет §2.6, аудит-лог, регламент инцидентов 24/72 ч |
| Обновление МИС ломает интеграцию | среднее | адаптер + контрактные тесты на тестовом контуре, дымовой тест после обновлений |
