# Голосовой контур клиники: транскрибация консультаций + команды «Инфоденту» голосом

**Что строим.** В каждом из 12 кабинетов — петличка и локальное приложение на компьютере врача.
Консультация пишется и расшифровывается на сервере клиники с разделением «врач / пациент».
Из расшифровки собирается: черновик для карты, план лечения, договорённости, рекомендации,
отчёт по консультации и разбор — **где и почему теряем пациента**, оценённый по методике,
которую врачи уже проходили на курсах в клинике.

Голосом врач даёт команды «Инфоденту»: создать план, записать пациента, поставить в очередь,
провести приём по такому-то плану. Бот делает то, что умеет через API, и **открывает готовое окно
с подставленными данными** — врач доформирует и подтвердит.

**Пишем только консультации.** Лечение не записываем: карты по лечению ведутся шаблонами, как и раньше.

Работаем над пунктами регламента **5, 6, 7, 8, 10**. Провожание, приживаемость и документирование
чек-листа не автоматизируем — задача системы прийти на пятничное собрание с готовым списком,
а не плодить бумагу.

---

## 1. Как это выглядит в кабинете

**10:00.** Врач открывает бота — расписание из «Инфодента». Тап по пациенту → **досье**: повод,
прошлые визиты, незакрытые планы, договорённости с прошлого раза, КТ и фото, долг. «Инфодент» не открывал.

**10:01.** «Начать консультацию». Врач проговаривает пациенту, что ведётся запись (это остаётся в самом
файле — лучшее подтверждение). Если пациент против — кнопка **«Без записи»**.

**10:02–10:35.** Консультация. Никто не печатает. По ходу врач может нажать педаль и продиктовать точное:
«Осмотр: зуб 36 — глубокая кариозная полость…», «План основной: имплантация 36, коронка на импланте 36».

**10:35.** «Завершить».

**10:42.** Готово: черновик карты под этого пациента (его жалобы его словами, а не шаблон), план лечения
с позициями из прайса, договорённости с датами, отчёт по консультации на страницу и разбор —
какие возражения прозвучали, как отработаны, на каком этапе потеряли, что пациент сказал между строк.

Врач читает, правит голосом или мышкой, жмёт **«Подтвердить»** — данные уходят в «Инфодент»
и координатору. Карта закрыта до того, как пациент вышел.

**Пятница.** Сводка за неделю готова сама: консультации, планы и суммы, сколько дошло до записи,
топ возражений, у кого и на каком этапе обрывается путь пациента, 3–5 записей с таймкодами для разбора.

## 2. Железо и контур

Всё внутри клиники: сервер в клинике, рабочие места в клинике.

| Что | Сколько | Комментарий |
|---|---|---|
| Петличный микрофон | **12** — по одному на кабинет | 1,5–2 тыс ₽; разделение говорящих делает софт, не второй микрофон |
| Ножная педаль push-to-talk | 12 | для диктовки команд, руки в перчатках |
| Сервер с GPU | 1 | распознавание + диаризация + разбор |
| Приложение-бот на компьютере кабинета | 12 | запись, команды, черновик, подтверждение |

**Нагрузка.** 12 кабинетов, ~40–60 консультаций в день по 20–40 минут = 20–30 часов аудио в сутки.
Обработка пакетная: результат через 5–15 минут после приёма, не в реальном времени — это сильно
удешевляет железо. Одна видеокарта на 24 ГБ такой поток тянет с запасом.

Если на каком-то кабинете акустика окажется плохой (эхо, шум из коридора) — там добавляется
второй микрофон ближе к пациенту. Это точечное решение по факту, а не закупка на всю клинику.

## 3. Транскрибация и разделение говорящих

Это ровно то, что делает Plaud, только внутри клиники и с вашей логикой поверх.

**Готовый стек, ничего изобретать не нужно:**

| Слой | Чем делаем |
|---|---|
| Распознавание речи | Whisper large-v3 (или GigaAM от Сбера — заточен под русский) |
| Разделение говорящих | **pyannote speaker-diarization 3.1** — на сегодня опорное решение; или NVIDIA NeMo |
| Сборка «кто что сказал» + таймкоды | WhisperX — связывает распознавание с диаризацией одним вызовом |

Врач и пациент — **два говорящих в тихом кабинете**, это самый простой случай для диаризации.
Одной петлички хватает: она пишет обоих, а разделяет модель. Дополнительно врача можно закрепить
как «спикера 1» по голосовому отпечатку смены — тогда роли не путаются между приёмами.

**Словарь клиники** (номера зубов, услуги вашего прайса, фамилии, сокращения) настраивается отдельно —
без него распознавание стоматологической лексики разочарует. Это настраиваемая работа на этапе запуска.

## 4. Курсы Поволоцкого как эталон оценки — ключевой элемент

У вас есть записи его курсов, проведённых в клинике. Это превращается в рабочий инструмент так:

1. **Транскрибируем записи курсов** тем же стеком, что и консультации.
2. **Извлекаем из них рубрику**: этапы консультации, что должно прозвучать на каждом, как
   отрабатываются конкретные возражения, какие формулировки рекомендуются. Черновик рубрики
   делает модель, **человек её один раз вычитывает** — из 20 часов курса вытащится каркас,
   но проверить формулировки должен тот, кто был на курсе.
3. **Рубрика становится чек-листом**, по которому система оценивает каждую консультацию.
4. **Обратная связь со ссылкой на источник**: не «закрытие не выполнено», а «на этом моменте по
   методике полагалось назначить конкретный следующий шаг с датой» — с цитатой из курса и таймкодом
   записи консультации.

Это и есть главное отличие от любого готового сервиса вроде Plaud: он расшифрует разговор,
но не скажет, где врач отошёл от **вашей** методики.

Технически: транскрипты курсов лежат в локальной базе, модель при разборе консультации сверяется
с ними (поиск по смыслу + рубрика в промпте). Обновили методику — перезалили материалы, ничего не переписывая.

## 5. Что система достаёт из консультации

**Фактура для карты и плана** — жалобы словами пациента, анамнез, что осмотрено, что озвучено,
какие суммы названы, о чём договорились.

**Разметка по этапам** (по рубрике из §4): контакт → выявление запроса → диагностика →
презентация проблемы → презентация решения → цена → работа с возражениями → закрытие.

**Метрики по каждой консультации:**

| Метрика | Что показывает |
|---|---|
| Доля речи врача / пациента | 80 % врача — это монолог, а не консультация |
| Сколько открытых вопросов задал врач | выявление потребности либо было, либо нет |
| На какой минуте впервые названа цена | цена раньше ценности — классическая точка потери |
| Была ли презентация проблемы до решения | решение проблемы, которой пациент не осознал, не покупают |
| Озвучены ли альтернативы | выбор без альтернатив читается как навязывание |
| Возражений прозвучало / отработано | отработано = тема закрылась, а не повисла |
| Было ли закрытие с датой | «я подумаю» без назначенного шага = потеря |
| Вопросы пациента без ответа | врач не услышал — частая и незаметная причина ухода |

**Скрытые сигналы** — то, ради чего стоит слушать запись:

| Фраза пациента | Что за ней | Что делать |
|---|---|---|
| «Надо посоветоваться с мужем» | решает не он, ЛПР не в кабинете | повторная консультация вдвоём |
| «А это точно нужно?» | провалена презентация проблемы | вернуться к диагностике, показать снимок |
| «У меня был неудачный опыт» | страх и недоверие, а не цена | отработать страх, а не давать скидку |
| «А попроще есть вариант?» | цена названа без ценности | альтернативы, этапность |
| «Сколько по времени?» | ограничение — время, не деньги | график, а не рассрочка |
| «Я подумаю» после цены | возражение не отработано | явная договорённость с датой |
| «Мне в другой клинике сказали…» | нужна аргументация отличий | разбор на собрании |

Каждый помечается **цитатой и таймкодом** — на собрании открываются нужные 30 секунд,
а не «давайте вспомним, как было».

**Отчёт по консультации** — страница текста + машиночитаемая структура:

```json
{
  "patient": {"infodentId": "IC-48213"},
  "doctor": "Иванов И.И.",
  "date": "2026-09-18T10:00",
  "reason": "боль при накусывании справа",
  "found": ["36 — кариес дентина", "отсутствует 46"],
  "offered": {
    "main": {"items": ["имплантация 46", "коронка на импланте 46"], "sum": 142000},
    "alt":  {"items": ["мостовидный протез 45-47"], "sum": 96000}
  },
  "priceNamedAtMin": 21,
  "talkRatio": {"doctor": 0.74, "patient": 0.26},
  "stages": {"contact": true, "needs": true, "problem": true,
             "solution": true, "price": true, "objections": "partial", "closing": false},
  "objections": [
    {"quote": "дороговато выходит", "type": "цена", "handled": true, "atMin": 23},
    {"quote": "мне бы с мужем посоветоваться", "type": "ЛПР", "handled": false, "atMin": 29}
  ],
  "hiddenSignals": [
    {"quote": "а это надолго? у меня в ноябре отпуск", "meaning": "ограничение по времени", "atMin": 26}
  ],
  "methodGaps": [
    {"stage": "closing", "expected": "назначить конкретный следующий шаг с датой", "source": "курс, блок 4"}
  ],
  "lossPoint": "закрытие",
  "agreement": {"text": "перезвонит после отпуска", "date": "2026-11-10", "owner": "координатор"},

```

## 6. Голосовые команды «Инфоденту»

Два уровня, работают вместе:

**Уровень 1 — через API.** Всё, что API позволяет сделать напрямую: создать план лечения из позиций
прайса, записать пациента на приём, поставить в лист ожидания, прочитать расписание и прайс.

**Уровень 2 — открыть готовое окно.** Там, где API не даёт записи (частая ситуация), бот открывает
нужное окно «Инфодента» с уже подставленными данными и заполненными полями — врач доформирует
и сохранит сам. Ровно то, о чём вы говорите: система делает, что может, а доктор доводит.

| Команда голосом | Что происходит |
|---|---|
| «Осмотр: зуб 36 — глубокая кариозная полость на жевательной, зондирование болезненно» | описание в карту, привязка к зубу 36 |
| «Диагноз 36 — кариес дентина» | диагноз + код, врач подтверждает |
| «План основной: имплантация 36, формирователь, коронка на импланте 36» | позиции по прайсу с кодами и суммой, слоты «по поводу / основной / альтернативный» |
| «Рекомендации: гигиена через две недели, направление к ортодонту» | озвучено / направления / договорённости с датой |
| «Отказ: дорого, вернётся после отпуска в ноябре» | код причины отказа + договорённость → задача координатору |
| «Записать на гигиену через две недели, утро» | свободные слоты из «Инфодента», выбор тапом, визит с комментарием |
| «В очередь на имплантацию, ждём решения до конца октября» | лист ожидания + структурированный комментарий |
| «Провести приём по основному плану» | открывает приём с подставленным планом |

Подбор по прайсу — нечёткий поиск: врач говорит «коронка на имплант 36», система показывает позицию
с кодом и ценой, врач подтверждает. Названия услуг берутся из «Инфодента» и обновляются автоматически.

Правка голосом: «исправь зуб 36 на 37», «убери формирователь из плана», «добавь контроль через месяц».

**Ничего не уходит в «Инфодент» молча** — всегда через подтверждение врача.

## 7. Куда уходит информация

| Кому | Что |
|---|---|
| «Инфодент» | карта (5,6,7), план (8), очередь (10), запись с комментарием |
| Координатор | что предложили, сумма, возражения, скрытые сигналы, договорённость, следующий шаг с датой, задача с дедлайном |
| amoCRM | по вашей действующей интеграции с «Инфодентом» — состав полей определяют координаторы |
| Врач | свой черновик карты, свои метрики консультаций |
| Управляющая, главврач | сводка за неделю, разрезы по врачам, топ возражений, точки потери |

**Отчёты без захода в «Инфодент»:** сервис сам читает данные по API и раскладывает — врачу вечером
(что не закрыто, договорённости на завтра), координатору утром (кого догонять сегодня),
к четвергу вечером — сводка на пятничное собрание. Тяжёлые выгрузки ночью, чтобы не нагружать боевую базу.

**Дорожная карта пациента** собирается из утверждённого плана автоматически: этапы, порядок, сроки,
суммы по этапам, что уже сделано.

## 8. Где стоит нейронка — от этого зависит вся правовая схема

Вы называли GigaChat и Алису. Разница между ними принципиальная:

| Вариант | Данные уходят | Что нужно юридически | Вывод |
|---|---|---|---|
| **Модель на своём сервере** (открытые веса GigaChat, Qwen и подобные) | никуда | ничего сверх того, что уже есть | **чище всего, рекомендую** |
| **GigaChat / YandexGPT в контуре** (корпоративная on-prem поставка) | никуда | договор с вендором | хорошо, но дорого — цена по запросу |
| **GigaChat / YandexGPT через облачный API** | Сберу / Яндексу | договор поручения на обработку (ст. 6 ч. 3), пункт в ИДС о передаче, псевдонимизация транскрипта перед отправкой | рабочий вариант при соблюдении всех трёх условий |
| **Алиса** | Яндексу, как потребительский сервис | договора поручения нет и не будет | **не подходит, исключаем** |

Алису я бы сразу убрал из рассмотрения: это ассистент для частных лиц, у него нет режима обработки
персональных данных по поручению оператора. Использовать его для данных о здоровье пациентов нельзя
независимо от того, что написано в ИДС.

Практичная схема, если пойдёте через облачный API: **перед отправкой транскрипт псевдонимизируется** —
ФИО, телефон, дата рождения заменяются на метки, обратная подстановка делается локально. Наружу уходит
обезличенный текст, привязка остаётся внутри клиники. Это снимает большую часть риска даже при облаке.

Зарубежные модели (ChatGPT, Claude, Gemini) — исключены: трансграничная передача спецкатегории
персональных данных.

## 9. 152-ФЗ: что должно быть закрыто

Сервер и рабочие места внутри клиники — значит, требование локализации баз данных в РФ (ст. 18 ч. 5)
выполняется, трансграничной передачи нет. Остаётся оформить саму запись.

**В ИДС (или отдельном согласии) должно быть прямо указано:**

- ведётся **аудиозапись консультации** — речи и врача, и пациента;
- **цели**: ведение медицинской документации, контроль качества оказания услуг, обучение персонала;
- **срок хранения** аудио и расшифровки;
- **кто имеет доступ** (лечащий врач, координатор, главный врач, управляющая — все под врачебной тайной);
- **право отозвать** согласие и порядок отзыва;
- если разбор идёт через облачную нейронку — **пункт о передаче обезличенного текста обработчику**
  с его наименованием (см. §8).

**Организационное:**

- [ ] Кнопка «Без записи» в боте — отказ пациента не должен ничего ломать
- [ ] Записываем только консультации, не лечение — минимизация по ст. 5
- [ ] Ответственный за обработку ПДн (ст. 22.1); актуализировать уведомление в Роскомнадзор (ст. 22)
- [ ] Политика обработки ПДн: оговорка, что **голос не используется для идентификации личности и
      голосовые модели не строятся** — иначе включается режим биометрии по ст. 11
- [ ] Модель угроз и уровень защищённости по ПП РФ № 1119 (спецкатегория → обычно УЗ-2), меры по приказу ФСТЭК № 21
- [ ] Ролевой доступ к записям + журнал обращений
- [ ] Срок хранения аудио (30–90 суток) с автоудалением; расшифровки — по решению клиники
- [ ] Регламент инцидентов: уведомление РКН за **24 часа** о факте и **72 часа** — о расследовании (ст. 21)
- [ ] Ознакомление врачей под подпись (запись используется в том числе для разбора консультаций)

Про ответственность, чтобы было на виду: с 30.05.2025 за утечки персональных данных действуют
оборотные штрафы (ФЗ № 420-ФЗ), ужесточена ст. 13.11 КоАП, работает ст. 272.1 УК РФ.

## 10. Сроки: что реально делается за неделю

Разделим то, что зависит от нас, и то, что зависит от вендора МИС.

### Неделя 1 — работающий прототип без «Инфодента»

За неделю собирается и запускается на 1–2 кабинетах:

| День | Что |
|---|---|
| 1 | Сервер, GPU, сеть, доступы. Параллельно — **письмо вендору МИС на API** (это долгий пункт, запускать в первый день) |
| 1–2 | Стек записи и расшифровки: Whisper/GigaAM + pyannote + WhisperX. Проверка на 5 реальных консультациях |
| 2–3 | Транскрибация записей курсов, черновик рубрики, вычитка человеком |
| 3–4 | Разбор консультации: этапы, метрики, возражения, скрытые сигналы, отчёт |
| 4–5 | Бот в кабинете: запись/стоп, «Без записи», экран черновика и отчёта |
| 5 | Прогон на реальных приёмах, правки |

К концу недели: **консультация записывается, расшифровывается, разбирается и приходит отчёт
координатору.** Это уже даёт ответ на «где теряем пациента» — и это независимо от «Инфодента».

Параллельно юрист готовит формулировки в ИДС (§9) — до первой записи реального пациента.

### Дальше — упирается не в код, а в вендора

Голосовые команды «Инфоденту» требуют **API-документации, домена и ключа домена**. Публичного описания
методов нет, доступ выдаётся по договору, часть функций включается платными тарифными опциями.
Сколько вендор будет это оформлять — от нас не зависит; закладывайте недели, а не дни.

**Как только доступ есть:**

- +3–5 дней: чтение (расписание, прайс, пациенты, визиты) и досье к приёму;
- +5–7 дней: команды на запись — план, запись на приём, очередь, через API или подстановку в окно;
- дальше: тиражирование на 12 кабинетов, отчётность на собрание.

Поэтому письмо вендору стоит отправить **сегодня**, а не когда прототип будет готов — иначе неделя
разработки упрётся в месяц ожидания доступа.

## 12. Риски

| Риск | Что делаем |
|---|---|
| Доступ к API затягивается | письмо в первый день; прототип §10 от этого не зависит |
| В API нет записи в карту/план | подстановка в окно «Инфодента» (уровень 2, §6) — закладываем сразу, а не как аварийный вариант |
| Функции закрыты платной тарифной опцией | стоимость выясняем вместе с документацией |
| Распознавание путает стоматологические термины | словарь клиники на запуске; проверка на реальных записях в первую неделю |
| Диаризация путает роли между приёмами | закрепление врача как постоянного спикера по голосовому отпечатку |
| Аналитике не верят на собрании | 30–50 консультаций размечает человек и сверяем с системой; цитаты с таймкодами вместо выводов |
| Пациент отказывается от записи | кнопка «Без записи»; доля отказов — отдельная метрика |
| Обновление МИС ломает интеграцию | вся работа с МИС в одном модуле + проверка после обновлений |
